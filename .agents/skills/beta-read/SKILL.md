# beta-read — 初読者視点の通読と興味監査

**批評は必ず新規コンテキストで行う。** 書いた本人・正典と計画を知った状態の
自分が読んでも「分かる人が分かるか」の確認にしかならず、「ここは後で回収
する」前提知識で我慢して読む・構造反復を「設計どおり」と正当化してしまう。
興味の採点も同じ — 自己採点はテストとして数えない。

## いつ使うか

- 話を書き終えたとき (short は全編、serial は話ごと・品質停車点)。
- 本文が退屈・分かりにくい・先が読めるという指摘を受けたとき。
- polish の前後で、削るべき箇所と残すべき引きを確認するとき。

## 外部化のしかた

重要なのは「正典・計画を読まない新規コンテキスト」であって手段はハーネス次第:

- **サブエージェント** (推奨): `export` した原稿だけを渡し、`canon/` `plan/`
  `entities.md` を一切読ませない。「読者と同じ無知」を強制する
- **別セッション・別チャット**: 新しい会話に原稿だけを貼る (正典を開かせない)
- **外部LLMへの貼り付け**: 一番無知な読者になる
- **自己再読 (最後の手段)**: 本文のみを読み直す。ただしこの場合も
  **面白さの評価は外部化する**まで合格にしない

## 入力

- export 済み原稿 (`python3 tools/export.py` で出した `out/<title>.md` か
  `build/` の対象範囲原稿)。**手作業で連結しない。**
- `templates/interest-scorecard.md` (採点する側が読む。原稿と一緒に
  「この観点で採点せよ」と渡す)
- 読者は本文が明示的に与えた知識だけを持つ。正典メモ・契約・計画の内容を
  読者知識として使わない。

## 読者として読む

- `[秘密]` は伏線効果の判断材料 — 「回収予定の秘密」が早漏気味なら指摘する。
- 「自分ならこう書く」趣味の指摘と、客観的に読者がつまずく点は分ける。
- **文芸的な上手さ・構成の綺麗さだけで甘く採点しない**: 破綻がなく小道具が
  回収されていても、淡々とした予定調和 (お使い進行) や、前提知識ゼロの読者を
  置いてけぼりにする説明不足があれば、心拍数と引っかかりの観点から正直に指摘する。
- severity は「読者離脱度」で較正する:
  high=実読者がこの本を閉じる / medium=読み飛ばす・流す / low=些細な違和 /
  info=参考。「書いた側には分かる」では severity を下げない。

## 手順

1. 対象範囲を決める (話単位が原則。short は全編)。
2. `python3 tools/export.py --workdir . --md` で対象原稿を出す。
3. 原稿だけを新規コンテキストへ渡す。渡すもの: 原稿 + 採点指示 (`docs/CRAFT.md` §11)。
   渡さないもの: `canon/` `plan/` `contracts/` `work.md` の設計。
4. **興味スコアカード (必須)**: `templates/interest-scorecard.md` の10観点を
   0–4 で採点する。各点の根拠を本文の具体 (行・台詞・描写) で書く。
   スコアだけ書かない。0–1=high / 2=medium / 3–4=問題なしに換算し、
   **high 1件以上 or medium 3件以上で不合格**。合計・平均は参考値。
   引用できない観点は0点、迷ったら低い方につける。
5. **診断用の問いに答える (心拍数・引っかかり・初見理解度の診断)**:
   - **離脱ポイント**: ここで本を閉じてもおかしくない退屈な箇所はどこか (行番号・話・引用)
   - **推進力と予定調和**: 先が読める「お使いシーン」になっていないか？ 読者が
     「次どうなる！？」と前のめりになる揺さぶりや予想外があるか？
   - **温度と人物の厚み**: 主人公が都合よく勝ちすぎたり、全員がキメ台詞ばかり吐いて
     淡々としていないか？ 敵役や脇役にも独自の理屈や人間味があるか？
   - **完全初見の理解度**: 元ネタや前提知識を一切知らない読者として、世界観の仕組みや
     因果関係に置いてけぼりになる箇所はないか？
   - **次を読む理由**: 次のページ・次話を読む理由は何か (残った問い・気になる人物・約束)
   - **最も記憶に残った具体物**・**予想を裏切られた箇所**・**感情が動いた箇所**
6. **findings を記録**: `reviews/beta-<対象>-<date>.md` に
   `templates/beta-review.md` の形式で。**スコアカード結果 (10観点の点と根拠、
   high/medium 件数) も同じファイルに記録する** (`reviews/interest-*.md` は
   作らない)。このファイルが判定の正本。
7. **閾値判定**: high 1件以上 or medium 3件以上 (`work.md` の興味の閾値で
   変更可) なら再改稿を発火する:
   - 原稿が `polished: false` なら、まず `.agents/skills/polish/SKILL.md` へ
     回す (ノイズ除去・具体化で直る finding を先に処理する)
   - polish 済み、または polish で解消しない (お使い進行・温度不足・構成の淡々等)
     → `write-scene` の興味 revise (最大2回、`docs/CRAFT.md` §4 の打開策カタログも
     任意活用) に回す
   - それでも超過 → auto は停止し、作者に「どこで離脱するか」「何が退屈か」
     を選択肢つきで報告する
8. **次工程の分岐**: 合格かつ `polished: true` →
   `.agents/skills/release-gate/SKILL.md`。合格だが未推敲 →
   `.agents/skills/polish/SKILL.md`。不合格 → 7の改稿。

## 出力・記録先

- `reviews/beta-<対象>-<date>.md` (スコアカード + 診断用の問い + findings + 結論)
- 必要なら `kind: revision` の変更セット、または新しい `writing_contract` 提案
- 合格判定と次工程を作者に1行で報告

## 注意

- 「正典との矛盾」は管轄外 — `.agents/skills/review-change/SKILL.md` で扱う。
- 意図的な難解さや特殊な語り口が作風として指定されている場合は `work.md` の
  検査ポリシーや `craft/voice.md` を踏まえて改稿方針を決める (ただしベータ読者には
  事前に渡さず、初見の反応をそのまま採る)。「退屈」は作風で正当化しない。
- スコアが高くても findings に「閉じる」「読み飛ばす」があれば不合格。

## アンチパターン

- 自己再読だけで面白さを評価し、外部化を省く。
- 正典・計画を読んだ状態で「読者」を演じる。
- スコアだけつけて根拠 (本文の具体) がない。
- 合計点が高いからと high finding を無視する。
- 「面白い」と断定して閾値判定を飛ばす。
- スコアカードを別ファイルに分けて beta-*.md に転記しない (正本は beta-*.md)。
