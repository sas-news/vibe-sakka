# beta-read — 初読者視点の通読と興味監査

**批評は原則として新規コンテキストで行う。** 書いた本人・正典と計画を知った状態の
自分が読んでも「分かる人が分かるか」の確認にしかならず、「ここは後で回収
する」前提知識で我慢して読む・構造反復を「設計どおり」と正当化してしまう。
興味の採点も同じ — 自己採点はテストとして数えない。

## いつ使うか

- 話を書き終えたとき (short は全編、serial は話ごと・品質停車点)。
- 本文が退屈・分かりにくい・先が読めるという指摘を受けたとき。
- polish の前後で、削るべき箇所と残すべき引きを確認するとき。

## 外部化のしかた

重要なのは「正典・計画を読まない新規コンテキスト」であって手段はハーネス次第。
サブエージェントが使えない環境でも、次のどれかで外部化する:

- **サブエージェント / workflow**: 原稿だけを渡し、`canon/` `plan/`
  `entities.md` を一切読ませない。「読者と同じ無知」を強制する
- **別セッション・別チャット**: 新しい会話に原稿だけを貼る (正典を開かせない)
- **複数セッション**: 話ごとに別セッションで読む (前話の記憶を持たせない)
- **役割を変えた同一セッション**: 「初読者」の役割を明示して読み直し、
  正典を参照しないことを自分に課す (弱い外部化。できれば避ける)
- **外部LLMへの貼り付け**: 一番無知な読者になる
- **人間の読者**: 作者・知人に原稿だけを読んでもらう (最も強い外部化)
- **自己再読 (最後の手段)**: 本文のみを読み直す。面白さの評価を外部化する
  まで「テスト済み」とは呼ばない

**記録は自己申告である。** `context: external` と書けば通るだけで、実際に
外部化したかを機械は検証できない。捏造を防ぐのは運用なので、公開前に
人間 (作者) のスポットチェックを推奨する — 1話だけ原稿を読んでもらい、
スコアカードの点数と根拠 (引用) が一致するか確認する。

## 入力

- export 済み原稿 (`python3 tools/export.py` で出した `out/<title>.md` か
  `build/` の対象範囲原稿)。**手作業で連結しない。**
- `templates/interest-scorecard.md` (採点する側が読む。原稿と一緒に
  「この観点で採点せよ」と渡す)
- 読者は本文が明示的に与えた知識だけを持つ。正典メモ・契約・計画の内容を
  読者知識として使わない。

## 読者として読む

- `[秘密]` は伏線効果の判断材料 — 「回収予定の秘密」が早漏気味なら指摘する。
- 「自分ならこう書く」趣味の指摘と、客観的に読者がつまずく点は分ける。
- severity は「読者離脱度」で較正する:
  high=実読者がこの本を閉じる / medium=読み飛ばす・流す / low=些細な違和 /
  info=参考。「書いた側には分かる」では severity を下げない。

## 手順

1. 対象範囲を決める (話単位が原則。short は全編)。
2. `python3 tools/export.py --workdir . --md` で対象原稿を出す。
   (作品に `tools/` が無い場合はキットの絶対パスで:
   `python3 /path/to/vibe-sakka/tools/export.py --workdir /path/to/work --md`)
3. 原稿だけを新規コンテキストへ渡す。渡すもの: 原稿 + 採点指示。
   渡さないもの: `canon/` `plan/` `contracts/` `work.md` の設計。
4. **興味スコアカード**: `templates/interest-scorecard.md` の10観点を
   0–4 で採点する。観点は目安であり、ジャンルに合わない観点は「対象外」と
   理由付きで外してよい。各点の根拠を本文の具体 (行・台詞・描写) で書く。
   スコアだけ書かない。0–1=high / 2=medium / 3–4=問題なしに換算し、
   **high 1件以上 or medium 3件以上は「改稿を検討する目安」**。
   合計・平均は参考値。引用できない観点は0点、迷ったら低めにつける。
5. **6つの質問に答える**:
   - どこで読むのをやめたか (行番号・話)
   - 次を読む理由は何か (残った問い・気になる人物・回収されそうな約束)
   - 最も記憶に残った具体物は何か
   - 予想を裏切られた箇所はどこか (意外と納得)
   - 感情が動いた箇所はどこか (どう動いたか)
   - 退屈した箇所はどこか (どこからどこまで、何が足りないか)
   - 既視感はどこにあるか (「どこかで読んだ」装置・人物・結末。なければ「なし」)
6. **findings を記録**: `reviews/beta-<対象>-<date>.md` に
   `templates/beta-review.md` の形式で。**スコアカード結果 (10観点の点と根拠、
   high/medium 件数) も同じファイルに記録する** (`reviews/interest-*.md` は
   作らない)。このファイルが判定の正本。
7. **判定材料をまとめる (公開停止条件ではない)**: high 1件以上 or medium
   3件以上 (`work.md` の興味の閾値で変更可) は「改稿を検討する目安」。
   超過したら次の材料を作者に示す:
   - 未推敲 (`polished: false`) なら `.agents/skills/polish/SKILL.md` を
     先に通す (削る・具体化で直る finding を処理する)
   - それでも超過するなら `write-scene` の興味 revise (最大2回) を提案
   - 改稿するか、そのまま公開するかは**作者が決める**。fail でも作者が
     公開を選べる (判定は材料であり、機械が公開の可否を決めない)
   - auto 運転中は自動公開せず、この判断を停止点として作者に渡す
8. **次工程の分岐**: `polished: true` で作者が公開可と判断 →
   `.agents/skills/release-gate/SKILL.md`。未推敲 →
   `.agents/skills/polish/SKILL.md`。作者が改稿を選んだ → 7の改稿。

## 出力・記録先

- `reviews/beta-<対象>-<date>.md` (スコアカード + 6質問 + findings + 結論)
- 必要なら `kind: revision` の変更セット、または新しい `writing_contract` 提案
- 判定材料 (スコアカード + findings) と次工程の候補を作者に1行で報告

## 注意

- 「正典との矛盾」は管轄外 — `.agents/skills/review-change/SKILL.md` で扱う。
- 意図的な難解さが作風として指定されている場合は `work.md` の検査ポリシーに
  従う。ただし「退屈」は作風で正当化しない (修正を検討する材料)。
- スコアが高くても findings に「閉じる」「読み飛ばす」があれば、公開前に
  作者へ強く改稿を勧める材料として扱う。
- 公開ゲートは「beta 未実施」を止めるが、**fail は停止条件ではない**。
  `interest_gate: fail` のまま公開するかは作者の判断 (警告として記録する)。

## アンチパターン

- 自己再読だけで面白さを評価し、外部化を省く。
- 正典・計画を読んだ状態で「読者」を演じる。
- スコアだけつけて根拠 (本文の具体) がない。
- 合計点が高いからと high finding を無視する。
- 「面白い」と断定して閾値と findings を作者に示さず、公開可否を決める。
- スコアカードを別ファイルに分けて beta-*.md に転記しない (正本は beta-*.md)。
