# plan-work — 計画立案 (planner)

計画は「イベント表」ではなく「面白さの仮説の連鎖」である。あらすじの時点で
面白くない計画は本文にしない。

## いつ使うか

- 話・シーンの骨格を作るとき、次のアークを計画するとき。
- 計画が退屈・同型・引きが弱いと言われたとき。
- 既存計画に話を挿入・並べ替えするとき (変更セットの判断もここで)。

## 入力

- `work.md` (mode・面白さの設計・憲章・ポリシー)
- `craft/engine.md` (欲求・対立・代償・時計・約束)
- `craft/voice.md` (声 — 場面の想定に使う)
- `plan/tree.md` (現状の骨格。空なら新規計画)
- `canon/facts.md` (確度ラベルつきのまま読む)
- `foreshadowing.md` (張設済みで未回収の伏線)
- 作者からの計画指示 (焦点・範囲)
- short では `work.md`・`craft/engine.md`・`plan/tree.md` で足りる。

## planner 役割プロンプト

> あなたは小説作品の「計画担当」です。読者が次を読みたくなるように、
> 話ごとの面白さの仮説を作ってください。各話に hook (冒頭の問い/異物)・
> promise (この話が読者に渡す快楽)・detonator (予想を裏切り、かつ納得させる
> 強いビート)・payoff (回収・報酬)・pull (章末に残す未解決の問い・予感)・
> structure tag (対峙/潜入/対話/移動/幕間 等)・skip test (この話を飛ばしたら
> 物語が壊れるか) を記入すると設計が安定します。短編では省略してもよいですが、
> 面白さの仮説だけはどこかに残してください。
> 各シーンにはタイトル・目的 (purpose)・
> 1文の要約を付けてください。1文の要約に意外性も代償もない話は、構成を
> 変えるか、捨てることを検討してください。既存計画がある場合は壊さない追加分のみ。
> 未確定 ([仮置き]/[未判断]/[意図的未確定]) の正典を確定事項として計画に
> 組み込まないこと。

出力案の形 (`plan/tree.md` に適用する形):

```
## 第N話 <タイトル> [draft]
- hook: <冒頭の問い/異物>
- promise: <読者に渡す快楽>
- detonator: <予想を裏切る強いビート>
- payoff: <回収・報酬>
- pull: <章末に残す未解決の問い・予感>
- structure: <対峙/潜入/対話/移動/幕間 等>
- skip test: <飛ばしたら壊れるか。壊れないなら削る/統合>
- シーン `N-1` <タイトル> [draft] <目的1行> — 契約: contracts/N-1.md, 本文: scenes/N-1.md
```

## 手順

1. 入力を読み、`work.md` のモード (short|serial) を確認する。
2. 各話の欄を埋める。short では話単位の簡易記入でよく、必要なら省略してよい
   (hook/promise/detonator/payoff/pull/structure/skip test は書くと設計が安定する)。
3. **あらすじ段階の面白さゲート**: 各話を1文で書く。その1文に
   (a) 意外性 (b) 代償 (c) 次を読む理由 のうち2つ以上がなければ構成を
   再検討する。通らない話は本文にしないことも選択肢。作者には却下案も添える。
4. **引きの連鎖を確認**: 前話の exit (章末の pull) が次話の hook に接続して
   いるか。全話の引きが同じ型 (「〜だった」で終わる等) になっていないか。
5. **構造の多様性**: 直近の話と同型 (同 structure tag) が2話以上連続して
   いないか。連続していれば構成を変えるか作者に相談する。
6. **先行範囲の確認** (標準値): 現在生成する話・シーンの目的と状態変化は
   詳細に確定 / 属するアークまたは短編全体の到達点と因果骨格を確定 /
   次の2単位の主要ビートを [約束済み] に / 全体結末は方式次第
   (blueprint なら必須、rolling なら未確定可)。
7. **提案として提示**: `proposals/p-NNNN-plan-<slug>.md` (kind: plan) に書き、
   既存計画との関係 (追加/変更/再構成) を明記する。
8. **承認後に適用**: `plan/tree.md` に話・シーンを追加 (状態 draft、
   シーンID `<E>-<S>`)。各話にアークの到達点・確度を注記。
   proposal の status を approved に更新。
9. **`dialogue.md`** に計画決定を追記する。

## 出力・記録先

- `proposals/p-NNNN-plan-*.md`
- `plan/tree.md` (hook/promise/detonator/payoff つき)
- `dialogue.md`

## 注意

- 計画ツリーの変更自体も変更管理の対象。承認済み計画を壊す追加・順序変更・
  削除は `.agents/skills/change-set/SKILL.md` で update_plan の変更セットにする。
- 章数を機械的に満たすことが目的ではない。「次の生成が後続を壊す自由すぎる
  賭けになっていないこと」と「読者が次を読みたくなること」が基準。

## アンチパターン

- イベント表・あらすじの清書を計画と呼び、面白さの仮説がない。
- hook が「状況説明」、detonator が「予定調和」になっている。
- 全話が同型の構造・同じ引きで、読者が先を予測できる。
- 話数を埋めるために中身のない話を計画する。
- 面白さのゲートを通さずに本文生成へ進む。
