# DIAGNOSIS — v1 はなぜ「1ミリも面白い作品」を作れなかったか

> 本稿は v1 の実運用で観測された失敗を、できるだけ具体的な証拠とともに記録し、
> v2 のどの機構がそれを防ぐかを対応づける。設計仕様は `DESIGN.md`、思想は
> `PHILOSOPHY.md`、技芸は `CRAFT.md` を参照。

## 0. 結論

v1 の失敗は「モデルの実力不足」ではない。**工程の欠落**である。

- 面白さを**設計**する工程がない (`spark` / `scene-craft` / `craft/engine.md`)
- 面白さを**検査**する工程がない (整合性レビューしかない)
- 文章を**改稿**する工程がない (`polish` が存在しない)
- 公開物を**選別**する工程がない (`release-gate` が存在しない)
- 代わりに帳簿の同期が品質のすべてを占め、モデルの注意力を食い尽くした

結果として、**整合性は通るが読む価値のない原稿**が「reviewed / 出荷可」と
判定されて公開された。

## 1. 失敗モードと証拠

### F1. 要約体が本文として出荷された

**観測**: 12話構成の「小説」が全編 8,500 字。1話あたり約 700 字。
各話は `一 / 二 / 三 / 四 …` のビート見出しで区切られ、各ビートは
1〜3 行の説明文。例:

```
五

秘密の暴露。

ソラのファンサイト「日々の残照」は、実は、全編を通じて一度も
更新が止まっていなかった。読めなくなった訳では、そもそも一度もない。
```

これは場面ではなく、**あらすじの清書**である。誰がどこで何をして、
何を感じ、何を選んだかが演じられていない。読者は「報告」を読まされる。

**なぜ起きたか**:

- 契約の要求が「必須イベントを含む」「企画書の見せ場を含む」だけで、
  場面として演じること・要約しないことを誰も要求していない。
- `write-scene` の writer プロンプトに「面白く書け」「場面として書け」が
  一行もない。あるのは「契約に従う」「矛盾を作らない」「禁止を破るな」だけ。
- 文字数目安 900〜1,400 字に対し実出力は約 700 字。下限が検査されていない。
- `review-01` は「禁止事項 OK / 秘密 OK / 未解決なし / 出荷可」と記録。
  文章が場面になっているかを見る観点がない。

**v2 の対策**:

- `AGENTS.md` ルール2 (要約を本文と呼ばない)。
- `write-scene` の興味監査 (ビート見出し・要約体・意図のない説明過多を失格)。
- `tools/manuscript_lint.py` L003 (`一` 単独行・`【…】` 見出し・本文中の `#`見出し)。
- `scene-craft` の skip test と「1文要約に意外性と代償があるか」。
- `beta-read` の興味スコアカード (「説明を読まされた」を high にする)。

### F2. 推敲が工程に存在しなかった

**観測**:

- 原稿末尾が `(了)` `◆` `(了)` と二重になっていた。シーン本文が `(了)` で
  終わり、export がさらに `(了)` と区切りを足していた。
- Markdown 原稿とテキスト原稿で区切り記号が不統一 (`◆` / `◇`)。
- 誤字が残存: 「あそこは、待つことそのものの墓標みたいな場所**だかなら**」
- 会話の破損: 「膨張パス」で本文を挿入した際、台詞が途中で壊れた箇所が
  2 件発生し、事後に修復された (修復自体はされているが、工程として
  「挿入で壊れる」ことが常態化していた)。
- 原稿の整合性レビューは「英文残留スキャン: クリーン」「出荷可」と記録したが、
  上記のアーティファクトは検査対象外だった。

**なぜ起きたか**:

- `polish` (推敲) という工程がなく、`review-change` は整合性と文体の
  「違和感」を低 severity で拾うだけ。文章を削る・具体化する・読み上げる
  パスが存在しない。
- `export` は「結合のみ。本文は一字一句変えない」と定義され、生成物の
  衛生 (重複・区切り・末尾) を検査する責任者がいない。
- export 後の原稿を**もう一度読む**工程がない。

**v2 の対策**:

- `polish` スキルを新設 (削る/具体化/声/リズム/章頭章末/アーティファクト除去)。
- `tools/manuscript_lint.py` L004 (重複) L009 (`(了)` 重複) L010 (区切り混在)
  L007 (stale export)。
- `release-gate` が `reviews/polish-*.md` の存在を必須化。
- `export` は `tools/export.py` 経由のみ。手作業連結を禁止。

### F3. 資料と作品の境界がなかった

**観測**:

- 作品の `out/` に、原稿のほかに**企画書 v1 / v2 (外部URL 15本以上を含む)**、
  EPUB 生成スクリプトが同居していた。公開物フォルダが作業机になっていた。
- `research/` の調査ノートは出典 URL 付きで管理されていたが、それを
  本文・成果物へ持ち込まないための規則がなかった。調査の「事実」と
  創作の「文章」の区別が運用者の注意力に依存していた。

**なぜ起きたか**:

- `out/` の定義が「export された原稿の出力先 (生成物)」と広く、何を置いて
  よいかの制約がない。
- `research` スキルは出典管理を強制するが、「引用ファイアウォール」
  (本文にコピーしない/URL を出さない) がない。

**v2 の対策**:

- `out/` は公開物のみ (`.md` / `.txt` / `.epub`)。`build/` を作業物の置き場に。
- `release-gate` が `out/` の混在を error にする。
- `tools/manuscript_lint.py` L001 (URL/出典/参照/資料/引用) L002 (台帳メタ)。
- `research` スキルに引用ファイアウォール節。`research-note.md` テンプレートに
  「本文への転用」欄 (言い換え・創作上の扱い) を必須化。

### F4. 分量インセンティブが逆だった

**観測**: 「契約の字数目安より不足していたため、revise パスを実施
(全シーン rev 2〜5)。**挿入式の追補**を行い、途中発生した台詞の破損 2 件を
修復。最終本文総量 約29,600字」。字数を満たす手段が「挿入」であり、
その副作用 (破損) の修復に工数が使われていた。

**なぜ起きたか**:

- 「分量の残差」を品質問題として扱う規範がない。字数は様式目安とされ、
  不足は「許容」と記録される一方、現場では膨張パスが走る。
- 削る工程がないため、文章の密度を上げる方法が「足す」しかない。

**v2 の対策**:

- `autonomy` で「膨張パス」を明示的に禁止。「場面化パス」(要約を場面に
  演じ直す) と「削減パス」(ノイズを削り、`craft/voice.md` の味と初見向けの
  最小限の補助線は残す) に置換。
- `polish` の原則「AI特有の冗長な言い換え・説明過多は容赦なく削り、`craft/voice.md`
  に定めた作品の温度・味を守る」。
- `write-scene` の文字数目安は**下限**として扱い、水増しを禁止。

### F5. 外部読者テストが最後の任意工程だった

**観測**: `beta-read` は v1 にも存在したが、実行は任意で、auto 運転の
「話ごとの停車点」でしか要求されない。実際の works では通読レビューが
整合性レビューの一部として自己文脈で行われ、「面白さの評価は必ず外部化する」
という v1 自身の注意書きが守られていない。

**なぜ起きたか**:

- 興味の評価基準が「読者が本を閉じるか」だけで、**読み飛ばす退屈**を
  修正に回す回路が弱い。
- 自己文脈の critic は「後で回収する予定」を知っているため、退屈を
  「設計どおり」と正当化する。
- スコアカードがなく、判定が感想の言い換えになりがち。

**v2 の対策**:

- `beta-read` に `templates/interest-scorecard.md` (10観点×0-4、アンカー付き)
  を必須化。判定は high 1 or medium 3。
- 「どこで読むのをやめたか」「次を読む理由は何か」を必ず聞く。
- 外部化の代替手段 (サブエージェント/別セッション/外部LLM) を明記。
- `autonomy` の品質停車点で必須化。

### F6. 帳簿が重すぎて、注意力が面白さに回らなかった

**観測**: 短編でも proposal → writing contract → changeset → review →
events → knowledge → foreshadowing の同期を要求。実運用の対話ログは
「契約を auto 承認」「正典追記」「変更セット適用」「レビュー」の記録で
埋まり、作品の面白さについての議論がほとんど残っていない。

**なぜ起きたか**: v1 の設計目標が「人間を情報管理者にしない」ことであり、
それは正しい。しかし**エージェントを帳簿管理者にしてしまった**。
帳簿は整合性の担保には効くが、面白さを1ミリも生まない。

**v2 の対策**:

- 短編モード (既定) では帳簿を最小化。契約1枚、正典は必要時のみ、
  変更セットは L2 以上のみ。推敲は変更セット不要の L0 工程。
- 帳簿の同期チェックは `tools/` と `release-gate` が機械的に行う。
- 浮いた注意力を `spark` / `scene-craft` / `polish` に使う。

## 2. 失敗を増幅した構造

1. **「検査に落ちないこと」が成功条件になっていた。** レビューの結論が
   「禁止 OK / 出荷可」であり、「面白いか」を問う欄がなかった。
2. **自己文脈の critic が自己正当化した。** 設計意図を知る検査者が
   「後で回収する」「意図的」と退屈を許容した。
3. **生成物の衛生に責任者がいなかった。** 原稿は export で生まれ、
   誰も最終ファイルを読まなかった。
4. **短編にも長編の規律を適用した。** 契約・提案・変更セットの同期コストが、
   短編の面白さを磨く時間を奪った。

## 4. 検証の考え方

v2 の成否は「lint が通るか」では測れない。次の3つで測る:

1. **衛生**: `tools/manuscript_lint.py` E 0、`release_gate` 合格、`out/` 清浄。
2. **興味**: 外部の初読者がスコアカードで閾値内。「次を読みたい」と答える。
3. **効率**: 短編1本あたりの帳簿ファイル数・同期往復が v1 より減っている。

このうち 1 は機械で自動化できる。2 は外部化が必須。3 は運用で測る。
v1 は 1 だけを測り、しかも 1 の一部 (衛生) すら測っていなかった。
